# ClipHub 分词系统二次分析与软编码无回归实施方案

> 分析基线：`beta-regex-settings-tabs-20260814`
> 基线 HEAD：`48a8ea3f4229250afdd95e9f0ce7ca677538f57e`
> 目标环境：ShortX / Rhino ES5 / Android
> 核心要求：以现有 UI、Regex、Repository、生命周期与性能优化为边界；尽可能配置驱动/Manifest 驱动；拒绝模块数量、文件名、规则 ID、资源路径、版本表等多点硬编码。

---

## 0. 结论

原《ClipHub Rhino ES5 分词系统 Jieba + Regex + Hybrid 完整实施方案》的方向可以保留，但实施前必须做一次结构性收口，否则分词功能本身可以做出来，后续新增模块/资源时仍会被现有硬编码拖住。

本次二次分析后的推荐方案为：

```text
现有 ch_17_tokenizer_ui.js
        │
        │ 只做 UI 桥接 / 状态渲染 / 选择结果
        ▼
新增 ch_19_tokenizer_service.js
        │
        ├── 生命周期 / Lazy Init / Worker / Cancel
        ├── Regex Adapter
        ├── Hybrid 调度
        ├── Tokenizer 配置
        └── Manifest Resource Resolver
        │
        ▼
新增 ch_18_tokenizer_core.js
        │
        ├── Dictionary Prefix
        ├── Block Scanner
        ├── DAG
        ├── DP Route
        ├── ASCII/数字合并
        └── User Dictionary Overlay

Manifest 非执行资源
assets/tokenizer/<dictionary>.gz.b64
        │
        └── 首次 jieba/hybrid 时加载
```

### 最重要的修正

1. **删除 Bootstrap `NAMES` 作为模块真源。**
2. **删除 `ch_15_app.js` 的 `order[]` 作为第二套生命周期真源。**
3. **删除 Preflight 中 `expected_module_count = 17` 和整套逐模块固定版本表。**
4. **不把词典打成大体积 JS 模块。**
5. **词典改成 Manifest 声明的非执行 Lazy Resource。**
6. **Regex 不复制实现，必须通过现有安全扫描链暴露统一 Adapter。**
7. **`generation` 只负责 stale-result 防护；另加 cooperative cancellation。**
8. **所有实际 Token Range 统一使用 `[start, end)` UTF-16 索引。**
9. **`ch_17_tokenizer_ui.js` 不做视觉、主题、Icon、窗口结构重构。**
10. **Rhino Worker 跨线程语义必须先真机 Probe，再决定 Executor 实现。**

完成这些修正后，本方案可以作为正式实现基线。

# 1. 证据等级

为避免 packed 模块内部函数名被猜测，本文统一使用以下等级：

| 标记 | 含义 |
|---|---|
| `[CONFIRMED]` | 当前分支源码/入口已直接确认 |
| `[PACKED-CONFIRMED]` | 模块为 GZIP/Base64 wrapper，但包装层、Review/Preflight 锚点已确认 |
| `[NEEDS-EXPAND]` | 文件已定位，内部精确函数名必须解包后确认，禁止猜名字直接修改 |
| `[NEEDS-DEVICE-PROBE]` | 代码路径可设计，但 ShortX/Rhino 真机线程语义必须实测 |

实施时应把 `[NEEDS-EXPAND]`、`[NEEDS-DEVICE-PROBE]` 当成前置门禁，而不是开发后补测。

### 受影响函数

#### `parseManifest(text, expectedRef)`

当前逻辑把 Manifest 数量与 `NAMES.length` 绑定：

```javascript

```

并以：


判断合法模块。

**问题：**

Manifest 并不是当前唯一真源。

新增：

```text

ch_19_tokenizer_service.js
```

即使已经加入 `module-manifest.json`，只要忘记同步改 `NAMES`，入口就会直接判定 Manifest 非法。

---

#### `verifyModules(moduleDir, manifest)`

当前：

```javascript
for (index = 0; index < NAMES.length; index += 1)
```

逐个验证。

**问题：**

模块验证范围来自入口硬编码，不来自 Manifest。

---

#### `installModules(...)`

当前：

```javascript
for (index = 0; index < NAMES.length; index += 1)
```

下载模块。

**问题：**

安装列表也是第三次使用 `NAMES`。

---

#### `loadModules(moduleDir)`

当前：

```javascript
global.ClipHub = {};

for (index = 0; index < NAMES.length; index += 1) {
    file = new File(moduleDir, NAMES[index]);
    eval(readUtf8(file));
}
```

**问题：**

真实执行顺序同样被入口硬编码。

---

### 修改结论

**删除 `NAMES` 作为文件列表。**

Manifest 的 `modules[]` 必须成为：

```text

校验列表
加载列表
模块文件数量
运行时描述
```

的唯一声明来源。

`ENTRY_VERSION` 不删除。

`ENTRY_VERSION` 属于入口协议版本，是安全兼容协议的一部分，不属于应该软编码掉的“偶然硬编码”。

# 7. 为什么 Manifest 软编码不能变成“任意远程代码都信任”

Manifest 驱动并不代表取消安全校验。

## `parseManifest()` 必须继续硬性验证以下协议

### 模块

```text
name:
    非空
    唯一
    必须为安全文件名
    禁止 /
    禁止 ..
    必须 .js

path:
    必须 src/
    禁止绝对路径
    禁止 ../
    规范化后仍必须位于 src/

sha:
    必须 40 位小写 hex

export:
    必须符合安全 JS Identifier 白名单

runtimeRole:
    仅允许：
    base
    managed
    passive
    app
```

### Resource

```text
id:
    唯一

purpose:
    仅语义标识，不作为文件路径

path:
    必须位于 assets/
    禁止 ..
    禁止绝对路径

encoding:
    仅允许声明过的安全 codec

loadPolicy:
    仅允许：
    on_demand
```

### 全局约束

必须：

```text
exactly one runtimeRole=base
exactly one runtimeRole=app
sourceRef == expectedRef
entryMinVersion <= ENTRY_VERSION
```

这类约束是安全协议，不属于应该删除的硬编码。

# 9. Resource 校验策略

## 9.1 不推荐二进制 `.gz` 直接进入当前同步链

当前：

```text
fetchRawFile()
    readBytes
    new JavaString(bytes, "UTF-8")

gitBlobSha(text)
```

本质是文本同步链。

如果直接加入：

```text
dict.gz
```

则必须把：

```text
fetch
write
hash
verify
rollback
```

全部扩展成二进制安全链。

这会扩大本次回归面。

---

## 9.2 推荐格式

源词典：

```text
dict.txt.small
```

构建阶段：

```text
UTF-8 dict
 ↓
GZIP
 ↓
Base64
 ↓
纯 ASCII 文件
```

得到：

```text
assets/tokenizer/jieba-small.gz.b64
```

它不是 JS。

因此：

```text
Bootstrap
    可以继续使用当前文本传输
    不会 eval
    不需要修改 binary transport

TokenizerService
    第一次 jieba/hybrid
    才 Base64.decode
    才 GZIPInputStream
    才 build Prefix
```

# 10. 启动阶段 Resource 不做大文件全文重复校验

安装/更新时：

```text
必须 SHA 校验 Resource
```

正常启动且本地 Package Manifest 未变化时：

```text
Module:
    启动时完整 SHA 校验

Lazy Resource:
    启动只校验存在性/Manifest 一致性
    首次真正使用时再完整 SHA 校验
```

理由：

```text
JS Module = 可执行
Resource = 非执行数据
```

这样能够避免为了一个用户可能永远不点击的分词功能，在每次 ClipHub 启动时读取整个词典资源。

首次加载失败：

```text
TokenizerService.state = FAILED
lastError = integrity_error / decode_error / dictionary_error
```

不得静默使用损坏资源。

```text

```

# 12. `loadModules()` 修改

签名：

```javascript
loadModules(moduleDir, manifest)
```

伪代码：

```javascript
function loadModules(moduleDir, manifest) {
    var modules = manifest.modules;
    var index;
    var item;
    var file;

    global.ClipHub = {};

    for (index = 0; index < modules.length; index += 1) {
        item = modules[index];
        file = new File(moduleDir, item.name);

        if (!file.isFile()) {
            throw new Error("Missing module: " + item.name);
        }

        eval(readUtf8(file));
    }
}
```

### 注意

文件加载顺序直接由：

```text
manifest.modules[]
```

决定。

不再从文件名 `ch_XX` 自己推导数字排序。

因此未来即使新增：

```text
ch_20_xxx.js
```

也不需要入口理解 “20”。

# 19. Regex Tokenizer Metadata 数据结构

推荐表：

```sql
CREATE TABLE tokenizer_rule_meta (
    rule_id INTEGER PRIMARY KEY NOT NULL,
    enabled_override INTEGER,
    priority_override INTEGER,
    group_override INTEGER,
    token_type_override TEXT,
    updated_at INTEGER NOT NULL,
    FOREIGN KEY (rule_id)
        REFERENCES regex_rules(id)
        ON DELETE CASCADE
);
```

### 为什么使用 override nullable

不在 SQLite 中重复写：

```text
enabled=1
priority=100
group=0
tokenType=regex
```

而是：

```text
NULL = 继承 Tokenizer Policy 当前默认值
```

这样后续修改默认策略时，不需要批量迁移历史行。

属于真正的软件配置继承，而不是在：

```text
数据库
Repository
UI
Service
```

四处重复默认值。

# 74. 最终原则

本次实现应坚持：

> **Manifest 是包声明唯一真源；Repository 是数据/Regex 唯一真源；TokenizerCore 是算法唯一真源；TokenizerService 是分词业务唯一真源；TokenizerUI 只是视图。**

以及：

> **软编码不是取消安全常量，而是消灭“同一个事实在多个文件重复维护”的硬编码。**

按这个边界实施，可以在不破坏当前 ClipHub 已有 Regex、UI、分页、IME、窗口及启动性能优化的前提下，把 Jieba / Regex / Hybrid 分词真正接入，并给后续自定义词典、自定义 Regex 分词规则、词性增强和新词典替换保留稳定扩展口。

# 75. 本轮补充硬化项

本节补充实施前必须加入方案的硬化点。优先级以 P0 / P1 标记；P0 进入 Manifest Contract 阶段，P1 可在 Resource Contract 阶段或后续收口阶段完成。

## 75.1 v1 本地 Manifest 离线兼容与迁移 `[P0]`

Manifest v2 上线时，入口必须保护已有用户的本地离线缓存。

当前离线回退链路为：

```text
readLocalManifest()
  ↓
parseManifest()
  ↓
verifyModules()
  ↓
offline-cache fallback
```

如果 `parseManifest()` 只接受 `schemaVersion=2`，已有 `module-manifest.local.json` 为 v1 的用户在断网启动时会失去离线缓存回退能力。

推荐实现：

```javascript
function parseRemoteManifest(text, expectedRef) {}
function parseLocalManifest(text, expectedRef) {}
function parseManifestV2Strict(text, expectedRef) {}
function parseManifestV1LocalCache(text, expectedRef) {}
function upgradeLocalManifestV1RuntimeShape(manifest) {}
```

规则：

```text
Remote Manifest:
    只接受 schemaVersion=2
    完整验证 modules/resources/runtimeRole/export/entryMinVersion

Local Manifest:
    优先按 v2 解析
    v2 解析失败后允许 v1 local-cache compatibility
    v1 兼容只用于 verifyModules + offline-cache fallback

联网成功后:
    local manifest 写回 v2 manifestText()
```

v1 兼容映射只用于本地缓存迁移边界：

```text
适用范围：已有 17 模块 v1 本地缓存
输出能力：moduleMap + 最小 runtimePlan
退出条件：成功拉取远端 v2 后覆盖本地缓存
```

v1 compatibility 不进入远端 v2 校验路径，也不作为新增模块声明来源。

验收：

```text
1. 本地只有 v1 module-manifest.local.json 且断网时，旧 17 模块可离线启动。
2. 联网获取 v2 manifest 后，本地缓存文件变为 schemaVersion=2。
3. 远端 schemaVersion=1 会触发协议错误。
4. 新增 ch_18/ch_19 只从 v2 manifest 获取。
```

## 75.2 `ENTRY_VERSION=8` 与 Manifest v2 绑定 `[P0]`

Manifest v2 引入 `runtimePlan`、`resourcePlan`、`resourceMap`、`runtimeRole`、`export` 等入口协议能力，应同步提升入口协议版本。

推荐修改：

```text
ClipHub.js:
    ENTRY_VERSION = 8

module-manifest.json:
    schemaVersion = 2
    entryMinVersion = 8

release_preflight.sh / manifest_contract.py:
    schemaVersion == 2
    entryMinVersion == 8
    ENTRY_VERSION == 8
```

绑定规则：

```text
schemaVersion=2
  ↓
entryMinVersion 必须为 8
  ↓
ClipHub.js ENTRY_VERSION 必须 >= 8
```

验收：

```text
1. v2 manifest + ENTRY_VERSION=8 通过。
2. v2 manifest + ENTRY_VERSION=7 失败，并提示入口需要更新。
3. v1 local cache 只走 75.1 的离线兼容路径。
```

## 75.3 Modules + Resources 统一 Atomic Sync / Rollback `[P0]`

Resource 引入后，模块和资源必须作为同一个 package transaction 处理。`resourceMap` 只能指向已激活目录。

推荐目录：

```text
runtimeDir/
  modules/
  resources/
  cache/module-manifest.local.json

sync staging:
  modules.stage/
  resources.stage/
  modules.backup/
  resources.backup/
```

推荐激活顺序：

```text
1. fetch remote manifest
2. parseRemoteManifest(v2 strict)
3. download modules -> modules.stage
4. download resources -> resources.stage
5. verify modules.stage SHA
6. verify resources.stage SHA
7. rename modules -> modules.backup
8. rename resources -> resources.backup
9. rename modules.stage -> modules
10. rename resources.stage -> resources
11. write local manifest atomically
12. loadModules(moduleDir, manifest)
13. App.start(context with modulePlan/resourcePlan/resourceMap)
14. commitSync 删除 backup
```

失败回滚：

```text
download/verify 失败:
    删除 stage
    保留当前 modules/resources/local manifest

激活后 loadModules/App.start 失败:
    删除新 modules/resources
    backup 恢复为正式目录
    local manifest 恢复 previousManifestText

commit 前中断:
    下次启动优先恢复 backup 或清理 stage
```

`sync` 对象需要记录：

```javascript
{
    updated: true,
    modulesBackup: backupModuleDir,
    resourcesBackup: backupResourceDir,
    previousManifestText: previousManifestText,
    moduleSetVersion: "...",
    downloadedModuleCount: 0,
    downloadedResourceCount: 0
}
```

验收：

```text
1. 模块成功、资源失败时，正式 modules 不被替换。
2. 模块和资源都激活后 App.start 失败时，两者一起回滚。
3. resourceMap 中全部路径指向 resources/ 正式目录。
4. local manifest 与正式 modules/resources 始终一致。
```

## 75.4 资源陈旧文件清理策略 `[P1]`

第一版资源安装推荐目录级替换：

```text
resources.stage -> resources
```


prune 只在成功启动后执行，避免回滚需要的旧资源提前删除。


## 75.5 Resource 完整性字段分层 `[P1]`

Resource 第一版继续沿用文本传输链，`.gz.b64` 文件按 Git blob SHA 校验。

推荐字段：

```json
{
  "id": "tokenizer.dictionary.default",
  "purpose": "tokenizer-dictionary",
  "path": "assets/tokenizer/jieba-small.gz.b64",
  "sha": "<git-blob-sha>",
  "encoding": "gzip+base64",
  "loadPolicy": "on_demand",
  "contentSha256": "<optional-dictionary-content-sha256>"
}
```

字段语义：

```text
sha:
    校验 manifest 声明文件本身，即 .gz.b64 文本文件的 Git blob SHA

contentSha256:
    可选诊断字段，用于校验解压后的词典原文内容
```

第一版必须实现 `sha`。`contentSha256` 可作为构建脚本和诊断输出字段保留。
